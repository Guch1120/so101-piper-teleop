# SO-101 → PiPER ローカル遠隔操作

オリジナルのSO-101リーダーからAgileX PiPERロボットアームおよびグリッパーを操作するためのLinuxブリッジです。LeRobotを介してUSBシリアル接続のリーダー情報を読み取り、SocketCAN経由でプロトコルv2のコマンドを送信します。ROS、ネットワーク中継、ティーチングモードでの記録は必要ありません。

詳細な[中国語README](../README.md)では、インストール、キャリブレーション、マッピング、すべてのCLIオプション、トラブルシューティングについて説明しています。[プロトコルに関する注記](PROTOCOL.md)および[検証範囲](VALIDATION.md)では、実測結果と制約事項を区別して記載しています。

## 対応ハードウェア

実機で使用した動作制御の中核部分は、ファームウェアS-V1.8-4を報告するPiPER 1台、オリジナルのSO-101リーダー、および1 Mbpsで動作するgs_usb/candleLight CANアダプターを用いてテストされています。Linux SocketCANが必要です。

衝突回避のための動作計画や、デカルト座標系での姿勢リターゲティングには対応していません。他の機体に移植する前に、その機体の関節可動範囲を確認してください。テストした機体のJ6の可動範囲は±180°ですが、すべてのPiPERモデルで同じとは限りません。

このブリッジは、アームの5つの関節を制御します。リーダー側のshoulder pan/lift、elbow、wrist pitch/rollを、それぞれPiPERのJ1/J2/J3/J5/J6に対応付けます。J4は制御引き継ぎ時の角度に固定されます。グリッパーの開口幅は別途制御されます。両アームの初期関節角度が一致している必要はありません。

## インストール

リポジトリをクローンし、そのディレクトリに移動します。

```bash
git clone https://github.com/ChenLing2345/so101-piper-teleop.git
cd so101-piper-teleop
```

続いて、以下を実行します。

```bash
sudo apt-get install -y python3-venv iproute2 psmisc can-utils
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -e '.[leader]'
piper-teleop --help
```

オプションの`leader`追加依存パッケージを指定すると、`lerobot[feetech]==0.4.3`とその依存パッケージがインストールされます。すでに互換性のあるLeRobot/Feetech環境が存在する場合、`pip install -e .`でこのブリッジのみをインストールできます。

CAN通信のみの診断やオフラインテストには、LeRobotもGPUも必要ありません。

## リーダーのキャリブレーション

`ls -l /dev/serial/by-id/`でシリアルポートを確認します。デバイスを永続的に識別できるby-idパスの使用を推奨します。

以下の例では`/dev/ttyACM0`を使用していますが、実際のリーダーのポートに置き換えてください。

```bash
export PIPER_LEADER_PORT=/dev/ttyACM0
```

すでに存在するキャリブレーションデータを使用するか、[公式SO-101セットアップ手順](https://huggingface.co/docs/lerobot/so101)に従ってください。

LeRobotによる初回キャリブレーションでは、リーダーのキャリブレーション値が書き込まれます。

```bash
lerobot-calibrate \
  --teleop.type=so101_leader \
  --teleop.port="$PIPER_LEADER_PORT" \
  --teleop.id=so101_leader
```

`--leader-id`には、キャリブレーション時と同じIDを指定してください。

`--calibration-dir`には既存のキャリブレーションディレクトリを指定できます。省略した場合、LeRobotがデフォルトのディレクトリを選択します。

PyPI公開版では`so_leader`実装を使用していますが、実機運用に使用したチェックアウトでは`so101_leader`を使用していました。このブリッジは、両方のインポート構成に対応しています。

ブリッジはキャリブレーションデータの読み取りと検証を行いますが、データを書き換えたり、リーダーのトルクを自動的に解除したりすることはありません。

## CAN通信と起動

すべてのコントローラーを停止した状態で、正しいCANインターフェースを設定します。

```bash
sudo ip link set can0 up type can bitrate 1000000
piper-teleop --diagnose-can --seconds 10
piper-teleop --seconds 10 --leader-port "$PIPER_LEADER_PORT"
```

診断モードとプレビューモードでは、CANフレームは一切送信されません。診断モードではリーダーへの接続も行われません。

アームを明示的に動作準備状態にした後、短時間の初期テストを実行します。

```bash
piper-teleop --prepare-can &&
piper-teleop --live --seconds 10 --speed 15 --accel 60 \
  --leader-port "$PIPER_LEADER_PORT"
```

**メーカー提供のリセット処理では、一時的にトルクが解除されます。必ずアームを物理的に支えてください。**

準備処理では、対応するリセット姿勢を確認し、実測姿勢に近い関節可動範囲内の目標値を事前設定したうえで、関節を有効化します。

任意のゼロ姿勢へ移動したり、グリッパーを操作したりすることはありません。

準備処理およびライブ制御への引き継ぎには、実際のターミナル上でオペレーターが`ARM`と入力する必要があります。

作業空間に障害物がないことを確認し、ハードウェアの非常停止スイッチをすぐに操作できる状態にしてください。

動作方向と作業空間を確認した後、連続運転する場合は以下を実行します。

```bash
piper-teleop --prepare-can &&
piper-teleop --live --seconds 0 --leader-port "$PIPER_LEADER_PORT" \
  --leader-id so101_leader --control-mode joint \
  --gain 1 --signs=-1,1,1,1,1 \
  --speed 60 --accel 240 --hz 100 --can-speed 100 \
  --max-offset 0 --wrist-mapping range \
  --gripper --gripper-speed 50 --gripper-effort 0.5
```

スペースキーで目標姿勢を保持して一時停止します。Cキーで基準姿勢を再設定して再開し、QキーまたはCtrl+Cで動作を停止して終了します。

ソフトウェアによる停止は通信が正常に機能していることが前提であり、物理的な非常停止装置の代わりにはなりません。

障害発生後の自動復旧や、以前の目標値の再送・再実行は行いません。

## マッピングと調整

- J1/J2/J3/J6は、制御引き継ぎ時の姿勢を基準とした相対的な関節角度の変化量を使用します。テスト環境では、J1の符号がデフォルトで反転されています。
- J5は、制御引き継ぎ位置から正負それぞれの方向に残されたリーダー側のキャリブレーション済み可動範囲を、PiPER側のJ5の残り可動範囲に対応付けます。`--wrist-mapping relative`を指定すると、以前の角度増分方式に切り替わります。
- `--max-offset 0`は、初期デバッグ時に使用していた追加の±90°ソフトウェア制限を解除します。ただし、実際の関節可動範囲制限は引き続き適用されます。
- グリッパー入力の0～100%は、デフォルトで開口幅0～70 mmに対応します。`--no-gripper`を指定しない限り、グリッパー制御は有効です。`--gripper-open-mm`で最大開口幅を小さくできます。effortはプロトコル上のトルクパラメータであり、校正された指先把持力を保証するものではありません。
- デフォルトの目標速度制限は60°/s、加速度制限は240°/s²で、制御周波数は100 Hzです。これらはソフトウェア上の制限であり、すべての負荷条件下で実機がこの性能を発揮することを保証するものではありません。
- `desired_deg`、`target_deg`、`actual_deg`は、それぞれ要求された動作、平滑化された指令値、実測フィードバック値を区別するための項目です。`loop_hz`および制限理由を示すフィールドは、問題の診断に役立ちます。

## 通信障害

実際に`NO_ACK`、bus-off、オーバーフロー、またはフィードバックの欠落が発生した場合、実行は停止します。

既知のgs_usbのERROR-ACTIVE通知は情報通知として扱われます。これには、従来形式のペイロード`0000000000005f00`も含まれます。

復旧処理によって、すでにラッチされた障害状態が解除されることはありません。

障害発生時のスナップショットは、以下のディレクトリに保存されます。

```text
${XDG_STATE_HOME:-$HOME/.local/state}/so101-piper-teleop/failures/
```

スナップショットには、元のエラー、CANフレームの経過時間、インターフェースのカウンター値の変化が含まれます。

以前から断続的に発生していたNO_ACKの物理的な原因は、まだ解明されていません。短時間のテストが成功しても、長時間運用での信頼性が証明されたことにはなりません。
